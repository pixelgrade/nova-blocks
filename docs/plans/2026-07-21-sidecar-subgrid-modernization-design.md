# Sidecar Layout Engine Modernization Design

Date: 2026-07-21
Status: Validated (design review with George, 2026-07-21)

## Goal

Modernize the Sidecar layout engine from a convention-enforced "fake subgrid" (every container re-declares one identical viewport-wide named-line grid and must overlap its parent perfectly) to a browser-enforced real `subgrid` architecture, replace the measurement-only break system with a layered hybrid (server-known → CSS `:has()` → measured `auto`), extend the block model to at most three areas driven by curated Layout Recipes on the Preset Engine, and fix every defect found in the 2026-07-21 system study — all without any saved-content migration and with an evidence-based ship decision from a before/after Studio comparison harness.

## Context: what the current system is

- One 13-track named-line grid (`fs ws frs gs cs gcs cc gce ce ge fre we fe`) defined in `packages/base-styles/mixins/_content-layout.scss`, re-instantiated on ~10 container types (`packages/core/src/scss/_layout.scss`), each pinned `grid-column: fs / fe !important` so all levels overlap pixel-perfectly and share one coordinate system.
- Semantic placement aliases (`--block-content-start/end`, `--block-wide-*`, `--block-full-*`, `--block-left/right-*`) as inherited custom properties; context (sidebar position, nesting) overrides them.
- `break-align-left/right` classes added by runtime JS collision detection (`packages/utils/src/break-align.js`) let wide/full blocks extend over the sidebar and left/right-aligned blocks jump into sidebar tracks (`grid-row-end: span 5`).
- Sidecar saves only `InnerBlocks.Content`; PHP renders the wrapper (`packages/block-library/src/blocks/sidecar/init.php`). Nothing layout-specific lives in saved markup — this is why no migration is ever needed.

Known defects (full study in the 2026-07-21 session; the ledger below carries every fix): unenforced perfect-overlap invariant, CLS from runtime-only break classes, order-dependent single-pass measurement with per-element reflow thrash, measurement before webfonts settle, `span 5` magic number, phantom sidebar tracks defining content width by subtraction, JS/SCSS container-list drift, one-shot overlap-set collection, sticky-fade leaving an invisible click-intercepting element, dead code, near-zero test coverage of the geometry logic.

## Decisions (settled in design review)

1. **Break model: hybrid.** Server-known and CSS-known cases stop involving JS; measurement survives only as the `auto` mode of an explicit per-block control (Auto / Always / Never), defaulting to Auto so existing content keeps its behavior.
2. **Block model: at most three areas, recipe-driven.** Content plus optional left and right rails. Geometry (rail existence, widths, asymmetric gutters, sticky, per-area type scale) is owned by a Layout Recipes family on the Preset Engine. No raw column-builder UI — generalized N-columns was explicitly rejected because Sidecar's moat is the shared site-aligned coordinate system with cross-area escape semantics, not "columns" (which core Columns already owns as isolated flex boxes).
3. **Migration: rewrite-first, evidence-based ship.** Develop the rewrite on a branch, compare against a baseline on the `sidecar-lab` Studio site; ship in-place under `@supports` if parity holds, gate behind a v2 flag only if real content breaks.

## Engine architecture

Split the current mixin into two roles:

- **`nb-layout-root`** — declares the 13 tracks and computes `nb-layout-settings`. Applied only where a coordinate system genuinely starts: root container, post content, template parts, and the intentionally independent small-scale instances (e.g. `supernova-item__inner-container`, which builds a card-internal mini grid and must NOT align with the page).
- **`nb-layout-passthrough`** — `grid-template-columns: subgrid`. **Narrowed by Task 2.1 evidence (permanent, not deferred):** the pass-through role applies only to *track-neutral* containers — `.nb-sidecar-area--content`, `.nb-sidecar--sidebar-none`, `.wp-block-query`, page-level `.nb-supernova`, and (later phase) Group. **Positioned sidecars stay track-declaring**: their width classes resize track vars locally, and subgrid inheritance cannot express nested layouts with different same-side rail widths at different depths (proven by the nested-deep fixture — custom properties don't flow upward). The modern rule is parent-scoped — `@supports (grid-template-columns: subgrid) { :is($nb-layout-grid-parents) > … }` — because `subgrid` on a non-grid-item computes to `none` and would collapse the layout (Anima's template-level Sidecar sits inside a non-grid `.wp-site-blocks`). Roots KEEP the `grid-column: fs/fe !important` pin: a root such as `.wp-block-post-content` can itself be a grid item of the template Sidecar's content area.

Deliberate carry-overs:

- The content area still spans `fs / fe` — subgrid children can only address lines inside the spanned range, and content children must be able to escape to full-bleed.
- The rail area stays a block container on desktop (rail children do not participate in the alignment system), spanning its region of the parent grid.
- Only columns are subgridded; row behavior (`grid-row: 1` areas, `grid-auto-rows: min-content`) is unchanged.

Fallback: all modern rules ship inside `@supports (grid-template-columns: subgrid)`; the current re-declared-grid math remains verbatim as the fallback, so pre-subgrid browsers render exactly today's output.

Track derivation flips — **as built in Task 2.2 (`315c718f`), which supersedes this paragraph's original naive reading**: a per-container `--nb-sidecar-content-width` is derived from the actual container minus rail budgets, and both content half-tracks hang off it (algebraic identity with the old per-side subtraction proven in review, exact in both `max()` regimes). The `:root` `--nb-content-width` token is deliberately byte-unchanged: **a custom property substitutes its `var()` refs at the element where it is DECLARED**, so consuming the root token per-container would bake in root defaults and silently discard Sidecar width classes (iteration 1 proved this with a +93.75px overflow the harness caught). Zeroing rail vars on rail-less roots is DEFERRED to Task 3.1: zeroed rails move the `gs`/`ge` lines that `--block-left-end`/`--block-right-start` anchor broken aligned blocks to, so it is safe only after the rail-absence classes re-anchor the break vars. Cross-repo consequence: Anima's reading-column workaround (napkin) stays necessary until the zeroing ships; if Anima/SM ever need a *live* per-context content width, that requires an element-level bridge var — the `:root` token cannot express it.

### Ship decision — Task 2.1 (2026-07-21): in-place `@supports`, conditional

Evidence (worktree commit `55afe4f0`, adversarially reviewed): fallback CSS byte-identical to the old engine except one 426-byte `@supports` rule in `build/core/style.css`; harness diff baseline↔subgrid exit 0 across all 68 captures with zero rect, break-class, element-set, or display differences (only kind-scoped `gtc` readout annotations, which structurally cannot mask geometry); 50/68 screenshots byte-identical, the remainder sub-pixel vertical drift within the documented tolerance. No v2 flag.

Conditions carried forward: (1) **editor smoke in Site Editor AND Post Editor before Phase 3 builds on the engine** — `build/core/style.css` provably ships to editor canvases via `enqueue_block_assets`; (2) **query-loop and supernova fixtures at the next re-baseline** — those two pass-through consumers currently rest on track-neutrality reasoning alone; (3) this section records the positioned-sidecar narrowing.

Known hazards (recorded, not blocking): third-party CSS that defeats `display: grid` on a container-union member (e.g. `#main { display: flex }` at (1,0,0) specificity) makes subgrid-capable browsers degrade *harder* (collapse) than fallback browsers (self-declared grid) — unreachable on the Anima stack, plausible on arbitrary wp.org installs. Subgrid items participate in the parent's *intrinsic* track sizing — the below-lap auto-track redistribution was proven geometry-neutral here, but it is the mechanism most likely to bite in overflow/min-content edge cases.

## Editor canvas preview (added 2026-07-21, George's directive)

The editor canvas is narrower than the frontend viewport (inspector sidebars eat width), so viewport-keyed breakpoints collapse the Sidecar to one column far too early — the desktop layout becomes un-previewable while the frontend is fine. Requirement: with the **Desktop device preview active, the editor renders the multi-column sidecar layout** (proportionally narrower tracks are acceptable); Tablet/Mobile previews key the collapse. Candidate mechanism: drive the collapse from the editor's device-preview state (and/or container-relative sizing) instead of raw canvas media queries, clamping rail widths so two-column geometry survives narrow canvases. Verify in both Site Editor and Post Editor.

### As built — Task 3.0b (2026-07-22): device-preview attribute bridge + editor-only desktop pin

Investigation (WP 7.0.2, live Post + Site editors, evidence in `.ai/sidecar-lab/editor-smoke/FINDINGS.md`): device preview is implemented by **resizing the canvas iframe** — Tablet → `width: 780px`, Mobile → `360px`, Desktop → the full available width (chrome eats ~280px, so a ~1300px browser yields a ~1020px canvas). The `below(lap)` media query fires against the iframe's own width, so all three cases collapse below 1024px. There is **no device-preview signal reachable from inside the iframe**: the canvas body/html classes are byte-identical across Desktop/Tablet/Mobile, and the outer `.edit-post-visual-editor` wrapper carries no `is-*-preview` class either (`useSimulatedMediaQuery` only rewrites top-window stylesheets and is a no-op for the iframed canvas). Therefore a Desktop preview at an ~780px canvas is **byte-indistinguishable inside the iframe from a Tablet preview at 780px** — pure CSS cannot separate "Desktop-preview-narrow" from "Tablet-preview", so a JS bridge is required (this satisfies the implementation plan's "JS bridge only if CSS alone cannot distinguish" gate).

Mechanism (frontend completely untouched — all of it lives in `editor-styles.scss` + an editor-only JS module):

- **Bridge** (`packages/block-editor/src/editor-canvas-device-preview.js`, imported by the package `index.js`): one edge-triggered `wp.data.subscribe` reads `core/editor.getDeviceType()` (the unified selector present in BOTH editors on WP 7; `core/edit-site`/`core/edit-post` experimental selectors kept as fallbacks) and writes `data-nb-device-preview` onto the canvas `.editor-styles-wrapper` (the iframe body, or the top-document wrapper on a non-iframed editor). DOM is touched **only when the device actually changes** (a rare explicit action), never per store tick — off the layout-recalculation path (napkin: Editor Performance). Desktop removes the attribute; the on-load default (Desktop, no attribute) already yields the pinned state, so the pin holds before the bridge first runs.
- **Pin** (`sidecar/editor-styles.scss`): scoped to `.editor-styles-wrapper:not([data-nb-device-preview="Tablet"]):not([data-nb-device-preview="Mobile"])`, it re-asserts the desktop coordinate template on a positioned Sidecar (`:not(.nb-sidecar--sidebar-none)`; its content area follows via subgrid), the desktop child spans on the Sidecar + content area, and the shared `nb-sidecar-desktop-layout`. Tablet/Mobile are excluded, so they collapse naturally through the unchanged frontend `below(lap)` rules.
- **Single source of truth (no drift):** the desktop template + child spans are extracted from `nb-layout-root` into `nb-layout-desktop-template-columns` / `nb-layout-desktop-content-columns` (`base-styles/mixins/_content-layout.scss`), and the Sidecar desktop block into `sidecar/scss/_desktop-layout.scss` (`nb-sidecar-desktop-layout`, invoked by `style.scss` under `@include above(lap)` and by the editor pin below `lap`). All pure extractions: frontend build CSS is geometry-identical (the only textual change is one cascade-neutral rule reorder inside an existing `@media` block).

Verified live in both editors × Desktop/Tablet/Mobile at a 1020px canvas (browser 1300px): Desktop keeps both rails at their natural widths (outer 309px, inner 216px — matching the above-`lap` ground truth) side by side; Tablet (781px) and Mobile (479px) collapse (`grid-row: auto`), with the bridge writing `data-nb-device-preview="Tablet"/"Mobile"`. Rail max-width clamp (`--nb-actual-container-width * 0.5 − gap*1.5`) already keeps the deepest nested-hive content column readable with no extra editor-side clamp: 484px @ 800px canvas, 388px @ 700px canvas (both > ~360px). Frontend invariant proven by the sidecar-lab harness: `task35 → task30b` = **0 differences** (my change is frontend-neutral); `baseline → task30b` = 0 unannotated diffs. Commit `1220c7ad`.

## Block model and Layout Recipes

- `sidecar-area` gains `areaName: sidebar-left | sidebar-right`. Legacy `areaName: sidebar` remains valid forever: PHP render and the editor map it to a side from the parent's `sidebarPosition` at runtime. No content migration. **Back-compat caveat (4.1 review):** the one edge outside the byte-identical envelope is pre-existing content with `sidebarPosition:none` PLUS a retained legacy sidebar area (reachable only by switching the radio to "none" while keeping the area) — old engine hid it, presence-driven engine renders it as a right rail. Low likelihood, arguably more correct (a present sidebar becomes visible); a fixture joins the matrix at the 4b.3 re-baseline.
- The Sidecar block accepts up to three areas: optional left rail, content, optional right rail. Existing two-area content is untouched.
- Geometry is a Preset Engine family (`sidecar-layout`). Managed attributes: rail existence and widths, asymmetric gutter offsets, sticky, content/rail font scales. Per the engine contract: every recipe declares the full managed set, the active recipe is derived by attribute comparison (never stored), applying is one `setAttributes()` patch, changed published recipes get new versions.
- Launch recipes: **Centered**, **Right Rail**, **Left Rail**, **Hive** (narrow meta rail · content · rail — the classic Hive magazine layout in one block), **Offset Editorial** (asymmetric empty gutter with no left area).
- The insert-time variation picker becomes the recipe picker. Nesting keeps working (pass-throughs chain) but stops being the only route to creative layouts.

### As built — Task 4.1 (2026-07-22): explicit area names + three-area model (worktree `f7eef766`)

The block-model half shipped (the recipe/Preset-Engine family is Task 4.2). Key as-built facts, some correcting the naive reading above:

- **Context-flow mechanism.** The legacy `sidebar` → side mapping runs off WordPress block context: `sidecar/block.json` declares `providesContext: { "novablocks/sidebarPosition": "sidebarPosition" }` and `sidecar-area/block.json` declares the matching `usesContext`. The PHP area render reads `$block->context['novablocks/sidebarPosition']` (native, bootstrapped to the client too). The **editor deliberately does not depend on context bootstrapping** — `sidecar-area/edit.js` reads the immediate Sidecar parent's `sidebarPosition` via `useSelect(getBlockRootClientId → getBlock)`, preferring `props.context` when present. A shared resolver (`novablocks_resolve_sidecar_area_side` in PHP, its JS twin in edit.js) is the single source of truth; the legacy `sidebar` default side is **right** (matches the SCSS default).
- **Rail-absence is area-derived, not position-derived.** Both the PHP wrapper render (parsed `innerBlocks`) and `sidecar/edit.js` (`useInnerBlocks`) resolve each direct area to a side and emit `nb-sidecar--no-left-rail` / `nb-sidecar--no-right-rail` from the ACTUAL rails — so a three-area sidecar emits NEITHER. A no-detectable-areas fallback preserves the legacy position-derived rails. Legacy two-area output is byte-identical (a single legacy `sidebar` resolves to exactly the old side).
- **Every rail area keeps the legacy generic `nb-sidecar-area--sidebar` class** alongside the resolved `--sidebar-{side}` — header/footer JS, sticky handling, and the `_content-layout.scss` nested-grid rule still key on it.
- **SCSS is rail-presence / per-side driven** (replacing the single-valued position rules): content narrowing on `.nb-sidecar:not(--no-left-rail)` / `:not(--no-right-rail)` (both narrow at once for three areas), rail placement on `.nb-sidecar > .nb-sidecar-area--sidebar-{side}`, and the layer-2 `:has()` empty-rail flip + per-block `nb-break-never` pin both per-side. The subgrid pass-through gate (`_layout.scss`) and the editor desktop-preview pin (`editor-styles.scss`) now key on the **both-rails-absent** signal instead of `sidebarPosition:none`, so a three-area sidecar stays track-declaring / multi-column regardless of its position value. All changes preserve two-area geometry exactly.
- **Carried per-rail fix (3.4 review):** `shouldSkipForCssCoveredRails` and `getAdjacentSidebarBlocks` (`packages/utils/src/break-align.js`) now inspect EVERY rail and take each rail's side from its own resolved class — an empty first rail beside an occupied second rail no longer skips incorrectly nor mislabels obstacles.
- **Live geometry proof (three-area, both rails filled, 1440px).** CSS resting state (no-JS): `--block-wide-start/end` compute to `cs`/`ce` and content/wide/full all render at exactly `cs→ce` (both narrowings active), with the left rail in `ws→gs`, right rail in `ge→we`, and body copy between them. With JS on, break-align opens wide/full over the short non-overlapping rails (correct classic-Hive reclaim). The editor renders all three areas side by side with the desktop pin and zero console errors.
- **Harness:** `--diff baseline task41` exits 0 — every one of the 68 differing captures is a pre-existing subgrid-readout / covered-skip annotation; Task 4.1 added zero new diffs (existing fixtures are all legacy two-area markup). No migration, ever.

### As built — Task 4.2 (2026-07-22): `sidecar-layout` Layout Recipes family (worktree `1e6813f1`)

The recipe/Preset-Engine half shipped. Five curated recipes replace the raw `sidebarPosition` radio as the PRIMARY control in the Sidecar Layout section; width/sticky/font stay as fine-tuning below (now gated on rail PRESENCE, so they surface for a three-area Hive whose position is `none`, and hide for Centered). Files: `packages/block-library/src/blocks/sidecar/layout-recipes.js` (pure family data + logic, zero WP imports — unit-tested against the real engine), `layout-recipe-controls.js` (picker + area reconciliation + apply), `layout-recipes.test.js` + `layout-recipe-controls-source.test.js`, and the rewired `inspector-controls.js`.

- **The structural-attributes decision (documented as the task required).** A Sidecar's rails are inner-block AREAS, not a serialized attribute, and the engine's managed patch is one `setAttributes()` — it can only write attributes. So rail existence is kept OUT of the managed patch entirely. The managed set is the FIVE style attributes only (`sidebarPosition`, `sidebarWidth`, `lastItemIsSticky`, `contentFontSize`, `sidebarFontSize`); NONE is a `STRUCTURAL_ATTRIBUTE` (cardLayout/layoutStyle/columns/contentType), so `getStructuralBoundaryViolations()` is empty by construction — the family cannot half-own structure. Rail structure is reconciled as a COORDINATED step (like the old position radio), never cleared implicitly. This is the strongest reading of the AGENTS rule available: rather than manage area structure as a "structural attribute written by every definition", the family manages NO structure at all and treats areas as a separate coordinated concern.
- **One-undo, both cases.** Structure already matches the target (attribute-only fine-tune, e.g. Right Rail↔Offset Editorial, or a legacy two-area whose `sidebar` simply follows the new position): the engine's single `getPresetApplyPatch()` → `setAttributes()`, block identity + inner content preserved. Structure must change (add/remove a rail): the SAME managed patch is embedded with the reconciled areas in ONE atomic `replaceBlock` — a single persistent change, so one undo reverts both. A `markNextChangeAsNotPersistent` + `replaceInnerBlocks` + `setAttributes` sequence was built first and REJECTED: proven live on a legacy two-area Sidecar, the non-persistent change folds into the PRECEDING checkpoint, so undo reverted the attributes but left the structure changed. Reconciliation preserves rail content (`cloneBlock`) and re-homes a rail's content when a side flips; a rail a recipe drops loses its content, restored by the single undo (no cross-apply stash — see the 4.2 review addendum).
- **Derivation = structural pre-filter + engine attribute match.** Two recipes can share managed values yet differ only in rails (Centered and Hive are both `none`/`small`), so the active recipe is derived by first filtering the family to recipes whose structural signature (which rails exist, read live from the inner blocks — observable, never a stored `presetId`) matches, then running `deriveActivePresetId()` by attributes. No structural match, or a structural match whose attributes diverge, is the first-class Custom state. Live: a fresh Sidecar derives to Centered; a legacy two-area with width `small` derives to Custom (no launch recipe matches that width).
- **Offset Editorial shape.** The design doc's "asymmetric empty gutter with no left area" and the alternative "empty-by-intent left rail" conflict. An empty left AREA was rejected — an empty area is structurally identical to (and therefore underivable from) Left Rail, and Task 4.2's concrete managed set has no gutter-offset attribute to split them. It ships honoring "no left area": content + a WIDE right rail (`sidebarWidth:large`), whose generous rail reads as the asymmetric offset, distinct from Right Rail (`medium`) by width alone. A TRUE empty-margin-with-no-area (the doc's literal geometry) needs the deferred `asymmetric gutter offsets` attribute — out of scope here, recorded as a future extension.
- **Hive one-block vs nested (measured, 1440px).** A single-block Hive carries ONE `sidebarWidth`, so both rails are equal-width (measured 216px each — symmetric). The nested-Hive fixture stacks two sidecars (outer `sidebar-left`/medium + inner `sidebar-right`/small), giving ASYMMETRIC rails (left 309px, right 216px). Both sit on the SAME named-line grid — rail anchor lines are identical (left rail at x≈158, right rail x≈1067→1283 in both; the right rail is byte-identical). The one-block recipe trades per-rail width control for single-block simplicity; this rail-width difference is expected and by design. Screenshots + probes in `.ai/sidecar-lab/task42-hive-compare/`.
- **Harness:** `--run task42 --force` then `--diff baseline task42` exits 0 (68/68 fully annotated, zero UNANNOTATED — no new diffs); `--diff task41 task42` = 0 differences (the recipe work is 100% editor-side; existing fixtures use no recipes). Query-loop and Supernova pages spot-checked live under the raised `:is()` pass-through — both resolve `subgrid`, neither collapses nor overflows.

## Break system (hybrid, cheapest layer first)

1. **Server-known (PHP, zero runtime) — as built in Task 3.1 (`18775c3c`).** A rail that doesn't exist is known at render: PHP emits `nb-sidecar--no-left-rail` / `nb-sidecar--no-right-rail`. The flip uses the **`inherit` keyword, not hard line names**: "an absent rail imposes no narrowing" = `--block-wide-start: inherit` — a hard `ws` flip clobbered the inherited `cs` constraint from an occupied *outer* rail in nested layouts (−270.8px regression, harness-caught). Rail-var zeroing shipped here too, via a per-container derived `--nb-layout-rail-*` that root overrides cannot leak into nested instances; every referenced named line keeps its exact position (collapsed width flows into the unreferenced `frs`/`fre` slack tracks), so the re-anchoring the Task 2.2 deferral note predicted proved unnecessary.
2. **CSS-known (`:has()`, zero JS) — as built in Task 3.2.** NOTE: this section's original selector (`:has()` nested inside `:has()`) is **invalid CSS** — the harness's no-JS mode exposed the dead rule where with-JS runs masked it. Valid form: `.nb-sidecar--sidebar-{left,right}:not(:has(> .nb-sidecar-area--sidebar > *)) > .nb-sidecar-area--content` flips that side's break vars AND pins the narrowed side's content var (`cs`/`ce`) — content vars alias the wide vars, so without the pin body copy reflows into the empty rail. Covers the Hive empty-column case with zero layout shift; proven: with JavaScript disabled entirely, wide/full blocks sit within 1px of their JS-run broken rects on the empty-rail fixtures at all four viewports.
3. **Geometry (JS, only `auto` with a partially filled rail).** Aligned blocks inside a Sidecar context get an inspector control — *Extend over sidebar: Auto / Always / Never* — serialized as a class, so Always/Never are SSR-stable. **As built in Task 3.3 (review round 2026-07-21):** the class (`nb-break-always` / `nb-break-never`) is written into the block's own `className` ATTRIBUTE on control interaction (the with-font-size-picker precedent) — there is NO save filter. This gives three properties at once: default (`auto`) output is byte-identical by construction (no deprecation, existing content can never invalidate); the editor canvas gets the class on the block wrapper for free (canvas parity — Never visibly constrains and Always visibly extends in the canvas); and saved markup survives Nova deactivation, because the class lives inside the block's serialized attributes rather than in filtered save output. The `sidecarBreak` attribute stays the source of truth the control reads; the class re-syncs only on control interaction (a hand-edited class field is never fought reactively). The measurement module is rewritten: runs after `document.fonts.ready` and image settle; batched read-phase/write-phase (no per-element class-toggle reflows); a second fixpoint pass only if any class changed; overlap sets re-collected on DOM change via one delegated observer. The editor reuses the module gated on structural signals, not full-canvas mutation storms.

**Layer 3 as built — Task 3.4 (`8d123ca9`), correcting this document's original CLS claim:** measured with throttled webfonts, **the old engine's CLS was already 0.00000** — it applied classes pre-first-paint at domReady; its real defect was *stale pre-fonts decisions kept silently* (the `e04f2aea` bug class). A literal fonts-gate would therefore have ADDED CLS by moving first application after paint. The built runtime keeps the pre-paint domReady pass and adds a correcting `fonts.ready` + image-settle re-run that shifts only when the stale decision was actually wrong; new-engine CLS stays 0.00000. Measurement is batched two-phase with a subtle required shape found empirically (three iterations to exact parity): pass 1 grant-biased in the all-extended world (the old top-down engine's attractor), pass 2 composite verification trimming real collisions — both all-extended-both-passes and composite-both-passes produce provable rect regressions. Frontend skips `:has()`-covered wide/full blocks (120 geometric no-op classes removed, classification-verified; pull-outs keep classes + honest computed row spans replacing `span 5`); the editor deliberately still measures them. **Review correction:** 4 of the 120 (alignfull figures on `right-medium`/`right-large-sticky-long` at 1440/2000) are not skips but genuine seed+verify decision divergences from the old engine, geometric no-ops only because layer-1's `--no-left-rail` opens that side anyway — the composite-verify mechanism could surface as visible geometry on content shapes outside the fixture matrix, so this is a recorded known residual, not a proven equivalence.

Sticky rail: the fade gains `visibility: hidden` and `pointer-events: none` (transitioned), and the RAF scroll loop is replaced with an IntersectionObserver between the sticky item and broken blocks.

## Pull-outs (alignleft/right: wrap, anchor, and rail escape)

Floats cannot work on grid items, so the grid engine can only produce *bands* (a paragraph squeezed beside the image for its whole length, dead space under the image). Scope expanded 2026-07-21 at George's request (text-wrap and mid-start asks, with screenshots on the right-medium and left-small fixtures):

- **Baseline behavior (unchanged default):** grid placement, but the `span 5` magic number dies — in Auto mode the measurement JS computes the real row span from following siblings; Always/Never apply; the `+`-sibling adjustment rules get tests.
- **Text wrap: Beside / Around (new, opt-in per aligned block).** *Around* uses **flow segmentation**: PHP groups the aligned block plus the following run of plain flow blocks (paragraphs, lists, headings) into ONE grid item spanning the content range that is a normal flow container; inside it the image gets a real CSS float, so text wraps beside AND continues under it. Rail escape still composes: track widths are known CSS vars, so a computed negative outer margin pulls the float over the rail (the classic Hive technique). Editor parity caveat, accepted for v1: the editor cannot re-wrap sibling blocks, so it shows the *Beside* approximation while the frontend renders the true wrap — stated in the control's help text; deeper editor parity is its own later design round.
- **New placements, not a modifier (George's direction, 2026-07-21).** Core Left/Right stay untouched as the defaults with today's semantics (content-edge anchor, auto-break over the rail). The mid-start behavior ships as *additional named placements* in the alignment vocabulary — working names **Left Content / Right Content**: the pull-out is bounded by the content column's center line (`cs → cc` / `cc → ce`, lines the nested-sidecar rules already use), with text taking the other half and, in *Around* mode, wrapping underneath (`width: 50%` + negative outer margin when floated). Serialized as a Nova placement class; core's `align` attribute is never repurposed.
- **DESIGN GATE CLOSED (2026-07-22, visual options round with George):** Phase 4b builds exactly two new placements, both wrap-based — **Content Around** (half-column-anchored float, text wraps beside AND under; left + right mirrors) and **Extend pull-out** (floated wrap pulled over the rail toward the wide edge via track-var margins — the classic Hive move). *Beside* (grid band) and *Into Rail* were considered and NOT picked. **Wrap segments align to the BODY edge** (the same edges surrounding body copy uses — ws→ce on Anima today), not the grid's content half, so wrapped text lines up with neighboring paragraphs. Implementation facts from the mockup round: Anima sets `clear: both` on paragraphs — the PHP flow segment must neutralize it inside the segment or wrapping silently dies; `is-resized` images pin the `<img>` width — placement CSS must override to fill; the feature always runs nested inside Anima's template-level sidebar-none Sidecar.
- **Alignment-vocabulary rethink is a Phase 4b design gate.** Before implementing, the full set (Left, Right, Wide, Full + new placements — possibly explicit rail placements replacing today's emergent "jump into the rail") gets one dedicated design round with George. Curated named placements only, never raw offset fields; *Text wrap* stays an orthogonal modifier applying to any left/right-family placement.
- **Fixture sequencing:** wrap/anchor fixtures are NEW capabilities with no old behavior to preserve; they get added only after the Phase 2 ship decision re-establishes the canonical baseline on the new engine (the differ's completeness check forbids growing the manifest mid-comparison).

### As built — Task 4b.1 + 4b.2 (2026-07-22): flow segmentation + Content Around / Extend (worktree `1f6749ed`)

Both placements shipped as one float-based mechanism riding a render-time flow segmentation. Key as-built facts, some sharpening the reading above:

- **Flow segmentation (`lib/flow-segments.php`), TDD contract-first.** A pure, WP-free grouping: when a Sidecar content-area child opts into a wrap placement, that block PLUS the following run of plain flow blocks (allowlist: `core/paragraph`, `core/heading`, `core/list`) becomes ONE `.nb-flow-segment` div. **Boundary rules:** the trailing run stops at the first non-flow block — the next aligned/wide/full block, another pull-out, a group, or a nested sidecar (none are in the allowlist; an *aligned* paragraph/heading also ends the run because it is a break block, not body copy). Each non-triggering block is its own passthrough. `tests/php/flow-segments-contract.php` covers trigger detection, the allowlist, the presence gate, every boundary case, segment classes, and render integration (added to the fast suite).
- **The no-op invariant is a hard gate, not a hope.** `novablocks_flow_segments_present()` is checked in the content-area render (`sidecar-area/init.php`) BEFORE anything is touched; with no opt-in it returns `$content` byte-for-byte. Proven by the harness: `--diff baseline task4b` exits 0 (68/68 annotated, ZERO new diffs — every existing fixture is untouched) and `--diff task42b task4b` = 0. When a pull-out IS present the children are re-rendered from the live `WP_Block` inner blocks (indices aligned with the parsed `innerBlocks` used for grouping).
- **Attribute shape (the documented decision).** ONE enum `sidecarWrap` = `none | around | extend` (default `none`, byte-identical), on the Task 3.3 `with-sidecar-break` family. The **side is derived from the block's own core `align`** (left/right), NOT a second `sidecarPlacement` attribute — a wrap only exists on a side-floated block, so `align` already carries the side and a parallel attribute would be redundant and could desync. Serialized through the className route (`nb-wrap-around` / `nb-wrap-extend`); `none` serializes nothing. Eligibility (`isSidecarWrapEligible`) is a side-floatable block (`image`/`group`/`quote`/`pullquote`) aligned left or right — heading/paragraph (wide/full only) are excluded.
- **Body-edge alignment is automatic, not a special span.** The `.nb-flow-segment` is a plain content-grid child, so it inherits the same `grid-column: var(--block-content-start)/var(--block-content-end)` as the body copy it replaces. Measured live (1440px): the segment's box edges are IDENTICAL to the surrounding body paragraph — `157.5→909.1` (right-rail) and `530.9→1282.5` (left-rail), to 0.0px. No `ws→ce` hardcoding was needed; matching the neighbour's computed span is inherent.
- **The `clear: both` fight was a specificity tie lost on source order.** Anima's neutralizer is `[class*=wp-block] { clear: both }` (common.css), and **WP 7 tags core paragraphs `.wp-block-paragraph`**, so it matches them at (0,1,0) and loads after Nova's block CSS. A plain `.nb-flow-segment > *` (also (0,1,0)) lost; the fix scopes it as `.nb-sidecar-area--content .nb-flow-segment > *` (0,2,0) — a segment only ever renders in a content area — so it wins unconditionally. Without this the copy silently dropped below the float (the documented gotcha, reproduced then fixed live).
- **Around vs Extend CSS (`sidecar/scss/_pull-outs.scss`, above `lap` only).** The segment is `display: flow-root` to contain the float for sizing without clipping overflow. **Around** = a 50% side float, no rail escape (measured beside=3 / under=2 paragraphs — the George screenshot case, beside AND under). **Extend** = a 52% float whose outer edge is pulled over the rail by a negative outer margin = `-(var(--nb-layout-rail-{side}) + var(--nb-sidecar-sidebar-{side}-gap))` — the derived TRACK VARS the content grid already resolves per container, never px. Measured (extend-right, 1440px): float right edge `1220.9` sits over the rail (`973.1→1282.5`), at/near the wide edge (the frs free track between rail and content is `1fr`, unaddressable, so "near" not "exactly"). Left mirrors. `is-resized` images had their `<img>` filled to 100% of the float box (measured `375.8`/`390.8px`, not the authored `420px` pin).
- **Pure CSS + PHP — no JS.** With page scripts disabled via CDP, the geometry is byte-identical to the JS-on run for both placements (segment, float, beside/under counts, extend margin all match). The break-align measurement layer is not involved.
- **Editor parity (accepted v1 divergence).** The editor cannot re-wrap sibling blocks, so the canvas shows the Beside approximation (the block's existing aligned grid placement); the control's help text states the published page renders the full wrap. No editor re-wrapping was attempted.
- **Deferred to Task 4b.3 (per the plan's fixture-sequencing rule):** wrap/extend fixtures are NOT added to the manifest here — the differ's completeness check forbids growing the manifest mid-comparison. Verification used temporary `sidecar-tmp-*` pages (deleted after) plus direct Playwriter measurement; the canonical fixtures join at the 4b.3 re-baseline.

#### Review addendum — Task 4b review (2026-07-22, worktree `ca276dea`)

- **Render-once via `pre_render_block` (was a double render).** The first cut re-rendered the content area's children inside the render callback — but WordPress had ALREADY rendered them once to build the `$content` the callback receives, so every inner block ran twice (a block with unique-ID or enqueue-once side effects would fire them twice). Fixed structurally: segmentation moved to a `pre_render_block` short-circuit (`lib/flow-segments.php`). `pre_render_block` fires for each inner block BEFORE WordPress renders it (`WP_Block::render` inner loop) and a non-null return makes WP skip its own render of that block entirely — so a pull-out content area renders each child EXACTLY once (via core `render_block()`), assembles, and wraps; every pull-out-free area returns null and renders normally (byte-neutral). The area render callback is back to a pure wrapper. Pinned by a counting-`render_block` contract (3 children → 3 calls; neutral path → 0 calls) and verified live (1 image / 5 paragraphs, no doubling). One WP-API gotcha: `WP_Block::__construct` array_merges the context arg, so `$parent_block->available_context` (which can be null) must be guarded to an array.
- **Wrap-wins (product ruling, George may override).** Never/Always + a wrap placement is contradictory — the wrap owns the geometry. Enforced three ways: (1) the "Extend over sidebar" break control is HIDDEN while a wrap is active (`getSidecarLayoutControlVisibility`, a pure tested helper), so no new contradiction can be authored — the serialized `sidecarBreak` is left untouched (no data loss; the control returns when wrap → none); (2) the JS measurement skip predicate (`shouldMeasureBreakClasses`) treats `nb-wrap-*` blocks as decided, so no `break-align-*` grid class is ever added; (3) CSS needed NO extra rule — a wrap block floats inside the `.nb-flow-segment` (flow-root), where the break class's grid placement is inert, so wrap wins structurally. Verified live: a block carrying BOTH `nb-wrap-around` and `nb-break-never` renders as Content Around (float, beside+under), the break class ignored. The class serializer still allows both markers to COEXIST in saved markup — wrap-wins is a UI + layout-ownership gate, not a class-stripping rule (pinned in the Jest coexistence test).
- **Mobile safety.** Below `lap` the float rules do not apply and a resized pull-out would keep its authored pixel width; a `max-width: 100%` cap on `.nb-flow-segment` images prevents overflow on a 375px column.
- **Harness:** `--run task4b2` → `--diff baseline task4b2` exits 0 (68/68 annotated, zero new diffs); `--diff task4b task4b2` = 0 (the render-once refactor + wrap-wins are frontend-neutral for existing content).

## Strategy tie-in (Pixelgrade LT)

Sidecar is defensible as the **layout contract of the LT design system**, not as a block: (1) a shared named-line editorial grid with cross-area escape is an engine competitors can't lift from markup (nothing layout-specific is saved); (2) Anima's reading column already IS the sidecar tracks — naming that officially yields a coherence promise ("your whole site sits on one grid") that fits LT positioning; (3) recipes are curation-over-configuration applied to layout — engine + core recipes free (LT must be credible standalone), deeper editorial recipes as Plus design depth; (4) the classic magazine identities (Hive, Pile) become reproducible LT starters and a legacy-customer landing path; (5) "the WordPress editorial layout engine" is an unclaimed position.
